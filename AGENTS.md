# Repository Guidelines

## Repository & Branch Workflow
- Development repository: `https://github.com/Intelli/opendbc.git`, local checkout `/Volumes/2TB/Documents/GitHub/opendbc`; develop on `ev9-dev`.
- `.github/workflows/ev9-sync.yaml` invokes `tools/ci/sync_ev9_branch.sh` after `ev9-dev` pushes. It copies the entire tracked tree into a new commit on `ev9`, preserving separate production history; identical trees need no commit. Treat `ev9` as generated output, not a development branch.
- Make changes requested through `/Volumes/2TB/Documents/GitHub/openpilot/opendbc/` in this standalone checkout's nested `opendbc/` package. Example: `openpilot/opendbc/car/hyundai/carcontroller.py` maps to `/Volumes/2TB/Documents/GitHub/opendbc/opendbc/car/hyundai/carcontroller.py`.
- Integration sequence: commit and push standalone `ev9-dev` changes when authorized, wait for its `ev9` sync, then update openpilot's `opendbc_repo` submodule to that synced `ev9` commit. Commit the updated gitlink in openpilot `ev9-dev` when authorized. Openpilot's `opendbc` is a symlink to `opendbc_repo/opendbc`; its recorded submodule commit controls the integrated version.

## Project Structure & Module Organization
- `opendbc/dbc/`: CAN DBC files and generator.
- `opendbc/can/`: Python parsers, packers, and tests.
- `opendbc/car/`: Brand-specific high‑level interfaces (e.g., `carstate.py`, `carcontroller.py`, `<brand>can.py`, `interface.py`, `fingerprints.py`, `values.py`, `radar_interface.py`).
- `opendbc/safety/`: C safety logic and tests; the test library builds with `cc` when imported.
- `examples/`: Small runnable examples (e.g., `examples/joystick.py`).
- `docs/`: User docs; `docs/CARS.md` is autogenerated—do not edit.

## Build, Test, and Development Commands
- Use Python 3.11–3.12 (`>=3.11,<3.13`) and this repository's `.venv`.
- Fast path (CI equivalent): `./test.sh` — sources setup, checks the lockfile, runs lint and tests, and builds safety libraries as tests import them.
- Install dependencies: `source ./setup.sh` uses `uv sync --all-extras --all-groups --inexact` and activates `.venv`. For an existing checkout, preserve the lockfile with `uv sync --locked --all-extras --all-groups --inexact`, then `source .venv/bin/activate`.
- Include dependency groups: the testing group supplies cppcheck and comma-car-segments; installing only pip extras is incomplete.
- Lint and tests: `lefthook run test`; tests alone: `unittest-parallel -j4`.
- Safety compilation uses the system C compiler via `opendbc/safety/tests/libsafety/libsafety_py.py`; no separate SCons build is required.

## Coding Style & Naming Conventions
- Python: use type hints; keep Ruff and ty checks clean.
  - Indent: 2 spaces; line length: 160 (`pyproject.toml`).
  - Run: `ruff check .` and `ty check` before sending PRs.
- C/C++ safety: keep to C11/C++17; cpplint and MISRA checks run in CI.
- Car ports follow the `opendbc/car/<brand>/` file names shown above.

## Testing Guidelines
- Framework: unittest; tests live under package folders (e.g., `opendbc/can/tests`) and use `test_*.py` naming.
- Parallel runs: `unittest-parallel -j4` (the lefthook/CI command).
- Targeted EV9 angle safety check, from the repository root: `.venv/bin/python -m unittest opendbc.safety.tests.test_hyundai_canfd.TestHyundaiCanfdLKASteeringAltEVAngleEV9 -q`.
- Full safety tests and coverage: `./opendbc/safety/tests/test.sh`.
- Safety/MISRA: `opendbc/safety/tests/misra/test_misra.sh` (invoked by lefthook/test.sh). Safety unit tests target 100% line coverage.

### Known Exceptions
- Temporary MISRA note: in `opendbc/safety/modes/hyundai_canfd.h`, the platform-ID extraction line
  `hyundai_canfd_platform_id = (param >> HYUNDAI_PARAM_CANFD_PLATFORM_ID_SHIFT) & HYUNDAI_PARAM_CANFD_PLATFORM_ID_MASK;`
  may trigger MISRA C:2012 10.1 (essential-type) warnings. For now, ignore this specific warning for that line; we’ll revisit a consistent casting style across safety code later.

## Commit & Pull Request Guidelines
- Commits: imperative mood, concise subject; scope prefix encouraged (e.g., `car/hyundai: adjust torque limits`).
- PRs must include:
  - Clear description of changes and rationale.
  - Tests for new behavior or safety changes.
  - Confirmation that `./test.sh` passes locally.
  - Any DBC or interface additions kept backward‑compatible when possible.
- Do not edit autogenerated files (e.g., `docs/CARS.md`).

## Security & Configuration Tips
- Never commit secrets, VINs, or proprietary vendor data.
- Ensure DBC contributions are legally shareable and attributed where required.
- For risky safety changes, explain hazards, mitigations, and provide targeted tests.
